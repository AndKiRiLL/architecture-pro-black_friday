# ADR:  Миграция на Cassandra: модель данных, стратегии репликации и шардирования

**Контекст:** Переход с MongoDB на Cassandra из-за проблем с решардингом при пиковых нагрузках (50 000 запросов/сек.)

## 1. Выбор данных для миграции

| Сущность | Миграция | Обоснование |
|----------|----------|-------------|
| **Заказы (orders)** | Да | Высокая нагрузка на запись, требуется геораспределение |
| **Корзины (carts)** | Да | Частые обновления, высокая нагрузка |
| **Товары (products)** | Нет | Частые обновления остатков, требуют строгой консистентности -> остаются в MongoDB |
| **Пользовательские сессии** | Нет | Хранятся в Redis (быстрый доступ) |

## 2. Модель данных

### 2.1 Заказы (orders)

```sql
CREATE TABLE orders (
  order_id UUID,
  user_id UUID,
  created_at TIMESTAMP,
  status TEXT,
  total_amount DECIMAL,
  geo_zone TEXT,
  items MAP<UUID, INT>,
  shipping_address TEXT,
  PRIMARY KEY ((user_id), created_at, order_id)
) WITH CLUSTERING ORDER BY (created_at DESC);
```

#### Обоснование

| Критерий | Как обеспечивается |
|----------|-------------------|
| **Равномерное распределение** | `user_id` имеет высокую кардинальность (много уникальных пользователей) -> хеш равномерно распределяет данные по нодам |
| **Эффективный доступ при нагрузке** | История заказов читается с одной ноды (`user_id`), без scatter-gather |
| **Горячие партиции** | Активные пользователи не создают проблему: `created_at` в кластерном ключе распределяет записи внутри партиции по времени, новые заказы не концентрируются в одной точке |
| **Минимизация решардинга** | При добавлении ноды Cassandra перемещает только часть данных (token range), а не все, как в MongoDB |

### 2.2 Корзины (carts)

```sql
CREATE TABLE carts (
  user_id UUID,
  session_id TEXT,
  status TEXT,
  items MAP<UUID, INT>,
  created_at TIMESTAMP,
  updated_at TIMESTAMP,
  expires_at TIMESTAMP,
  PRIMARY KEY ((user_id), session_id)
);
```

#### Обоснование

| Критерий | Как обеспечивается |
|----------|-------------------|
| **Равномерное распределение** | `user_id` имеет высокую кардинальность -> равномерное распределение по нодам |
| **Эффективный доступ при нагрузке** | Получение корзины по `user_id` - точечный запрос к одной ноде, минимальная задержка |
| **Горячие партиции** | Гости с `user_id = null` выделены в отдельную таблицу (`carts_guest`), чтобы не создавать "горячую" партицию для всех гостей |
| **Минимизация решардинга** | При добавлении ноды перемещается только часть данных (token range), без полного перераспределения |

```sql
-- Отдельная таблица для гостевых корзин (изоляция "горячей" партиции)
CREATE TABLE carts_guest (
  session_id TEXT PRIMARY KEY,
  items MAP<UUID, INT>,
  created_at TIMESTAMP,
  expires_at TIMESTAMP
);
```

## 4. Стратегии целостности данных

| Стратегия | Описание | Применение |
|-----------|----------|------------|
| **Hinted Handoff** | Если нода недоступна, координатор временно хранит запись на другой ноде и отправляет её позже, когда нода восстановится | Включена по умолчанию для всех таблиц |
| **Read Repair** | При чтении данных сравниваются версии с разных реплик, устаревшие обновляются | Для **orders** и **carts** (критичные данные) |
| **Anti-Entropy Repair** | Фоновый процесс, который сверяет Merkle-деревья на разных нодах и восстанавливает расхождения | Для **orders** (гарантия целостности) |

### Обоснование

| Сущность | Стратегия | Причина |
|----------|-----------|---------|
| **orders** | Read Repair + Anti-Entropy (ежедневно) | Заказы критичны, требуется максимальная согласованность. Read Repair проверяет данные при каждом чтении, Anti-Entropy — фоновое восстановление для редких расхождений |
| **carts** | Read Repair (только при расхождениях) | Частые обновления, допустима небольшая задержка. Проверка только при обнаружении конфликтов |
